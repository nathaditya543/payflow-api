# PayFlow API

A simplified, database-backed REST API for a UPI-style wallet system — register users,
look them up, and record money transfers between them. Built with Spring Boot 3,
Spring Data JPA, and an in-memory H2 database.

## How to run the app

Prerequisites: JDK 17+ (no local Maven install needed — the project ships the Maven Wrapper).

```bash
./mvnw spring-boot:run
```

(On Windows, use `mvnw.cmd spring-boot:run`.)

The app starts on **http://localhost:8080**. The H2 in-memory database is created fresh
on every startup (no data survives a restart — see the Persistence answer below for why
that matters for a payments app).

- H2 console: http://localhost:8080/h2-console
  - JDBC URL: `jdbc:h2:mem:payflowdb`
  - User Name: `sa`, Password: *(blank)*
- Base API paths: `/users` and `/transactions`

To run the automated tests: `./mvnw test`

## Project layout

```
src/main/java/com/payflow/payflowapi/
  entity/      User.java, Transaction.java        (JPA-mapped tables)
  repository/  UserRepository.java, TransactionRepository.java  (Spring Data interfaces)
  service/     UserService.java, TransactionService.java        (business logic)
  controller/  UserController.java, TransactionController.java (REST endpoints)
```

### What each layer does

- **entity** — plain Java classes annotated with `@Entity`/`@Id`/`@GeneratedValue`. These
  are the only place the database schema is described; Spring Data JPA (via Hibernate)
  reads the annotations and generates the `CREATE TABLE` statements at startup. No SQL
  DDL is hand-written.
- **repository** — interfaces extending `JpaRepository<Entity, IdType>`. We never
  implement these; Spring Data generates a proxy implementation at startup that provides
  `save`, `findAll`, `findById`, etc., plus any derived/custom query methods we declare
  (see Task 3/6 below).
- **service** — `@Service`-annotated classes that hold the business logic and are the
  only layer that talks to repositories. Controllers never call repositories directly;
  this keeps HTTP concerns (status codes, JSON) separate from persistence concerns.
- **controller** — `@RestController` classes that map HTTP verbs/paths to service calls
  and serialize the return value to JSON automatically (via Spring's built-in Jackson
  message converter — no manual JSON handling).

## Where Spring Boot's three headline features show up in PayFlow

1. **Embedded server** — there is no separate Tomcat installed or configured anywhere in
   this project. `spring-boot-starter-web` pulls in an embedded Tomcat, and
   `SpringApplication.run(...)` in `PayflowApiApplication.java` starts it in-process.
   Running `./mvnw spring-boot:run` gives you a listening HTTP server on port 8080 with
   zero server configuration files.
2. **Auto-configuration** — we never wrote a `DataSource` bean, an `EntityManagerFactory`,
   or a `DispatcherServlet` registration. Because `h2` and `spring-boot-starter-data-jpa`
   are on the classpath, Spring Boot's auto-configuration detects them and wires up an
   in-memory H2 `DataSource`, a Hibernate `EntityManagerFactory`, and transaction
   management automatically. `application.properties` only nudges a few of the defaults
   (`ddl-auto`, `show-sql`, the H2 console path) rather than declaring everything from
   scratch.
3. **Production-ready defaults** — sensible behavior out of the box: JSON error responses
   with the right HTTP status codes (try `GET /users/999` — you get a 404, generated by
   `ResponseEntity.notFound()` plus Spring's default error handling, not a raw stack
   trace), automatic `Content-Type: application/json` negotiation, and Spring Boot's
   startup banner/logging showing exactly which port and profile it's running with. Actuator
   was not added here to keep the assignment scoped to Tasks 1–6, but it would slot in
   the same way — add the dependency, get `/actuator/health` for free.

## Task 3 — the SQL behind `findByUpiId`

Declaring this one line in `UserRepository`:

```java
Optional<User> findByUpiId(String upiId);
```

produces this query at runtime (captured from the console with `spring.jpa.show-sql=true`,
after calling `GET /users/upi/priya@okaxis`):

```sql
select
    u1_0."user_id",
    u1_0."balance",
    u1_0."name",
    u1_0."phone_number",
    u1_0."upi_id"
from
    "user" u1_0
where
    u1_0."upi_id"=?
```

(Column and table names are quoted because `spring.jpa.properties.hibernate.globally_quoted_identifiers=true`
is set in `application.properties` — needed so the `User` entity can map to a table
literally named `USER`, which is otherwise a reserved keyword in H2.)

**(a) How JPA derives it from the method name** — Spring Data JPA parses the method name
into subject + predicate keywords. `findBy` is the subject keyword (return matching
entities); everything after it, `UpiId`, is matched — case-insensitively, with camelCase
segments — against a property on the `User` entity. Since `User` has a `upiId` field,
Spring Data builds a query equivalent to `SELECT u FROM User u WHERE u.upiId = ?1` and
compiles it into the SQL above. No implementation is written by hand; the method name
*is* the query specification.

**(b) What the `?` placeholder means** — it's a JDBC bind parameter (a `PreparedStatement`
placeholder), not literal text substitution. The method argument (`upiId`) is bound to it
at execution time by the JDBC driver, which is what protects this query from SQL
injection — user input is never concatenated into the SQL string.

## Task 6 — three ways to write a custom query, compared

| Approach | Example in this project | Pros | Cons |
|---|---|---|---|
| **Derived method name** | `findByUpiId(String upiId)` | Zero SQL to write or maintain; refactor-safe (rename the field, the method must follow); very readable for simple lookups | Method names get unwieldy fast for anything with multiple conditions, ordering, or joins |
| **`@Query` (JPQL)** | `findUsersWithBalanceAbove(Double amount)` using `SELECT u FROM User u WHERE u.balance > :amount` | Full query flexibility (joins, aggregation, projections) while staying database-agnostic — JPQL operates on entity/field names, not table/column names, so it still works if we switch from H2 to Postgres | You have to write and maintain the query text yourself; typos aren't caught until runtime unless you enable query validation |
| **Native SQL** (`@Query(nativeQuery = true)`) | *(not used here)* | Access to database-specific SQL features JPQL can't express (vendor functions, hints, window functions) | Ties the code to one database's SQL dialect — breaks portability, bypasses Hibernate's entity-aware validation, and column-name typos are only caught at runtime. This is why it's the **least preferred** of the three: it gives up the main benefit of using an ORM (database independence) for a small syntactic convenience, and should only be reached for when JPQL genuinely cannot express what's needed. |
